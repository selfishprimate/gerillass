# Aspect Ratio

<Member name="aspect-ratio">

The **Aspect Ratio Sass mixin** holds an element to the ratio you give it, and
writes the declarations the CSS property leaves you to find out about:
`object-fit`, so an image is cropped rather than stretched, `border: 0` for an
`<iframe>`'s 2px default border, and `height: auto`, so a `height` attribute
cannot beat the ratio.

</Member>

<Hint kind="warning">

**New in Gerillass 2.0.0.** This mixin replaces **Ratio Box** and **Responsive
Video**, which were byte-identical to each other and are both gone. It goes on
**the element itself**, not on a wrapper around it. See [Coming from Ratio Box
or Responsive Video](#coming-from-ratio-box-or-responsive-video).

</Hint>

## Arguments

<Arguments of="aspect-ratio" footnote="Pass null as the second argument to leave object-fit out of the output entirely.">
  <Argument name="$ratio (16/9)" type="string, number, function">
    The ratio to hold. Accepts a slash separated string such as <code>16/9</code>, a colon separated string such as <code>16:9</code>, a bare number, where <code>1.5</code> means 1.5 to 1, or <code>var()</code>, which is written as it is. Left out it is <code>null</code>, which is read as <code>16/9</code>. Anything else is refused with an error.
  </Argument>
  <Argument name="$fit (cover)" type="string">
    Sets the <code>object-fit</code> property. Accepts <code>fill</code>, <code>contain</code>, <code>cover</code>, <code>none</code>, <code>scale-down</code>, or <code>null</code> to leave <code>object-fit</code> alone. The default is <code>cover</code>.
  </Argument>
</Arguments>

## Images and embeds with a height attribute

The two are for different moments, which is why an element carries both.

The `width` and `height` attributes are read before the file arrives. The
browser divides one by the other, holds that much space open, and the rest of
the page does not jump when the image lands. They are not a size: an `<img>`
with `width: 100%` is as wide as its container, not 1400px. Writing them is the
usual advice against layout shift, and embed codes write them on their
`<iframe>` for you.

The mixin's ratio is for afterwards. It is the shape you want the element to
be, whatever proportions the file itself has, and `object-fit` decides what
happens to the picture inside that shape.

They collide in one place. A `height` attribute is also a definite height, and
with `width: 100%` also definite the browser has both dimensions already and
ignores `aspect-ratio` entirely. Measured in Chrome 152, Firefox 156 and Safari
26.6.2 in a 300px box, before 4.0.0:

| Element | Before 4.0.0 | Since 4.0.0 |
|---|---|---|
| `<img width="1600" height="900">`, ratio 4:3 | 300 × 900 | 300 × 225 |
| the same image inside `<picture>`, a flex item or a grid item | 300 × 900 | 300 × 225 |
| `<iframe width="560" height="315">`, ratio 16:9 | 300 × 315 | 300 × 169 |
| `<video width="640" height="480">`, ratio 16:9 | 300 × 480 | 300 × 169 |

Since 4.0.0 the mixin writes `height: auto` in a rule of its own, inside
`:where()`:

```css
:where(.element) { height: auto; }
```

A `height` attribute counts for less than any rule, so this one overrides it.
But `:where()` has no specificity, so a `height` your stylesheet sets, before
the include, after it, or through an element selector, still wins: a `<div>`
with `height: 400px` stayed 400px tall in all three browsers. A plain
`height: auto` in the mixin's own rule would have shrunk it to 225px.

<Example
  caption="The file is a 1400 by 933 photograph and the attributes say so, so the browser reserves the right space before it arrives. The mixin then holds the element at 4:3 and crops the photograph into that."
  resizable
  hint="Drag the right edge. The attributes never make the image 1400 by 933; the ratio is what decides its height."
  listing="<img class=&quot;element&quot; src=&quot;/images/landscape.webp&quot; width=&quot;1400&quot; height=&quot;933&quot; alt=&quot;A wide landscape at first light&quot;>"
>
```scss
.element {
  @include aspect-ratio("4:3");
}
```
```html
<img class="element" src="/images/landscape.webp" width="1400" height="933" alt="A 4 by 3 box holding a cropped photograph" />
```
</Example>

<Example
  caption="If you want the ratio without the rest of the mixin, `validateRatio` accepts the same values and returns just the ratio. The compiled CSS beside it is the whole output: one declaration, with no `object-fit`, `border` or `height` to go with it."
>
```scss
.element {
  aspect-ratio: validateRatio("16:9");
}
```
</Example>

## What it refuses

A ratio the browser cannot read stops the build. A string ratio separates its two numbers with a slash or a colon, and anything else, a dash included, is refused rather than written into the declaration for the browser to drop.

```scss
.element {
  @include aspect-ratio("16-9");
}
```
```text
Error: `16-9` is not a valid ratio. A string ratio must separate width and height with `/` or `:`, like `"16/9"` or `"16:9"`.
```

A fit that is not one of the five `object-fit` keywords is refused too, with the list.

```scss
.element {
  @include aspect-ratio("16:9", squish);
}
```
```text
Error: `squish` is not a valid $fit for `aspect-ratio`. Pass one of: fill, contain, cover, none, scale-down, or null to leave object-fit alone.
```

## Coming from Ratio Box or Responsive Video

Both of those mixins held a ratio with a `padding-top` hack, a pseudo-element
and an absolutely positioned child. The CSS `aspect-ratio` property made all of
that unnecessary, and it left the two mixins identical to each other, so they
were replaced by this single one.

The rename itself is mechanical. What is not mechanical is **where the mixin
goes**: the old mixins were applied to a wrapping element, and this one goes on
the element itself.

```scss
// Before, on a wrapper
.hero  { @include ratio-box("16/9"); }
.video { @include responsive-video("16/9"); }

// After, on the element
.hero  { @include aspect-ratio("16/9"); }
.video iframe { @include aspect-ratio("16/9"); }
```

<Hint kind="warning">

**This part is easy to get wrong.** A ratio on a **wrapper** does not size an
`<iframe>` inside it: the iframe keeps its intrinsic 300 by 150. Measured in a
browser at a container width of 640px, a ratio on the wrapper gives a 640 by 360
wrapper with a 304 by 154 iframe inside it, while a ratio on the iframe itself
gives 640 by 360 with no wrapper needed.

</Hint>

If you have a wrapper `<div>` around a video embed only to hold its ratio,
remove the wrapper along with the old mixin.
