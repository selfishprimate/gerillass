# Breakpoint

<Member name="breakpoint">

The **Breakpoint** Sass mixin writes a `@media` query around whatever you put
inside it. Sizes come from the breakpoint map by name or are written out as
lengths, and the two mix freely in the same stylesheet.

Ranges are the part worth knowing: a range that ends at a named breakpoint ends
*just under* it, so the range below a name and the range above it meet exactly,
with nothing applying twice and no width falling between them.

</Member>

<Hint kind="info">

The names live in `_map-for-breakpoints.scss` and follow Bootstrap's: `xsmall` at 0, `small` at 576px, `medium` at 768px, `large` at 992px, `xlarge` at 1200px and `xxl` at 1400px, which is new in 4.0.0. **Add your own or replace them there.**

</Hint>

## Arguments

<Arguments of="breakpoint" footnote="`between` takes its two sizes as one space-separated pair: `breakpoint(between, small large)`. Two sizes with no mode mean the same thing.">
  <Argument name="$mode" type="string">Which <code>width</code> condition to write: <code>min</code> from a width upwards, <code>max</code> up to a width, <code>only</code> at exactly that width, and <code>between</code> for a range. It can be left out when you pass two sizes, since a pair can only mean a range.</Argument>
  <Argument name="$value" type="number (with unit)">The width, as a name from the breakpoint map or a length in any unit a width condition takes: <code>px</code>, <code>em</code>, <code>vw</code>, <code>cqi</code>, <code>0</code>, <code>calc()</code>. A percentage, a bare number, another unit and a word that is not a key are refused, because the query they would write never matches. So is <code>var()</code>: a custom property is not evaluated in a <code>@media</code> condition, so the rule would never apply.</Argument>
</Arguments>

<Hint kind="warning">

**Why 0.02px under, and not one pixel?** A range used to end at `767px`, which left every fractional width a scaled display produces falling into the gap, and 16px of gap with a map written in `rem`. It ends 0.02px under a pixel key now, and 0.01 of a unit under one in `rem` or `em`. CSS's own range syntax would say the same thing, but Safari drops the whole rule before 16.4.

**This only happens with a name.** A length you write out is used exactly as you wrote it, so `breakpoint(between, small 1199.98px)` ends where it says.

</Hint>

<Example caption="Two sizes with no mode are the same range, since a pair can only mean one thing, and `only` writes a query for a single width.">
```scss
.element {
  @include breakpoint(small, large) {
    background: #5bc0bb;
  }

  @include breakpoint(320px, 768px) {
    background: #69995d;
  }

  @include breakpoint(only, 1200px) {
    background: #ed6a5a;
  }
}
```
</Example>

<Hint kind="warning">

**One width on its own is a single pixel.** `breakpoint(320px)` compiles to `@media (width: 320px)`, so the styles apply when the viewport is exactly 320px wide and nowhere else. Since 2.2.0 the mixin warns about that form. Pass `min` to style from a width upwards, or `only` to say you meant the one width.

</Hint>

## What it refuses

A size no width condition can match stops the build. Until 2.3.1 these compiled: a name missing from the map went into the query as it was, so `breakpoint(min, huge)` wrote `@media (min-width: huge)`, which a browser keeps and never applies, with nothing to say so. Measured in Chrome 152, the same was true of a percentage, a bare number such as `768`, and a unit that is not a length.

```scss
.element {
  @include breakpoint(min, huge) {
    color: red;
  }
}
```
```text
Error: `huge` is not a breakpoint. $map-for-breakpoints has xsmall, small, medium, large, xlarge, xxl; pass one of those, or a length such as `600px`.
```

The names are case-sensitive, so `"MEDIUM"` is refused the same way.

```scss
.element {
  @include breakpoint(max, 50%) {
    color: red;
  }
}
```
```text
Error: `50%` cannot be used as a size in `breakpoint`: a width condition takes a length, and one written with `50%` would never match in @media. Pass a length such as `600px`, `40em` or `calc(30em + 1px)`, or a key from $map-for-breakpoints.
```

A length written as a string, `breakpoint(min, "600px")`, still works, as it always has.

`between` takes two sizes. One used to stop the build with Sass's own message
about a list index, and a third was used for nothing and never mentioned; both
are named now.

```scss
.element {
  @include breakpoint(between, 768px) { color: red; }
  @include breakpoint(between, 100px 200px 300px) { color: red; }
}
```
```text
Error: `between` takes two sizes separated by a space, and `768px` is 1. Write a start and an end, `breakpoint(between, small large)`, or use `only`, `min` or `max` for a single width.
Error: `between` takes two sizes separated by a space, and `100px 200px 300px` is 3. Write a start and an end, `breakpoint(between, small large)`, or use `only`, `min` or `max` for a single width.
```

A range also has to be able to match, and two shapes cannot. Both compiled
until 4.0.0, into valid CSS a browser keeps and no width ever satisfies, so the
styles inside simply never applied.

```scss
.element {
  @include breakpoint(large, small) { color: red; }
  @include breakpoint(medium, medium) { color: red; }
}
```
```text
Error: `large, small` is not a range `breakpoint` can match: it runs backwards, since 992px is wider than 576px. Pass the smaller size first.
Error: `medium, medium` is not a range `breakpoint` can match: both ends are the same width, and a range ends just before the key it names, so the query asks for at least 768px and under 768px at once.
```

A range of one width written by hand is a different thing and still works,
since a length ends at itself: `breakpoint(768px, 768px)` applies at exactly
768px, which is `only` written another way.
