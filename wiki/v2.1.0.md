# v2.1.0

Four new members and one accessibility fix. Nothing breaks, so there is no
migration for anyone. The work in the other repositories is additive.

Signatures and argument details come from `gerillass.json`. What is written
out below is the part that is not in there: why each member exists, and the
measurements a documentation page should be built on.

| Member | Kind | Status |
|---|---|---|
| `container` | mixin | new |
| `container-query` | mixin | new |
| `line-clamp` | mixin | new |
| `fluid` | **function** | new |
| `loadify` | mixin | behaviour changed |

the site, not something to do by default.

## What each member is for, and the measurement behind it

Every one of these exists because something silently does not work. That is
the bar the library holds itself to, and the failing case is what the
documentation page should open with, because it is what the reader is about
to get wrong.

### `container` and `container-query`

Component-level responsiveness. `container-query` takes the same argument
shapes as `breakpoint`, so the two read alike: a size, two sizes for a range,
or `min`/`max`/`only`/`between` followed by a size. Sizes resolve through
`$map-for-breakpoints`, though a raw length is the common case because a
container is usually narrower than the viewport.

```scss
.card  { @include container("card"); }
.title { @include container-query("min", 400px) { font-size: 2rem; } }
```

```css
.card { container-type: inline-size; container-name: card; }
@container (min-width: 400px) { .title { font-size: 2rem; } }
```

**The measurement.** An element is not matched by a `@container` rule that
reads its own container. In a browser, a 600px element carrying
`container-type: inline-size` did **not** match `@container (min-width:
400px)`, while a child of it did. A second run showed that an element with no
container ancestor at all matches nothing. Both fail silently: no warning, the
rule is simply never applied.

So the page has to say plainly that the container goes on an **ancestor** of
whatever the query styles.

Named containers are passed as a `$name` keyword rather than positionally,
because `container-query("card", "medium")` could not be told apart from
`container-query("min", "medium")`.

### `line-clamp`

`ellipsis` truncates one line; this truncates several.

```scss
.excerpt { @include line-clamp(3); }
.full    { @include line-clamp(none); }
```

```css
.excerpt {
  display: -webkit-box;
  -webkit-box-orient: vertical;
  -webkit-line-clamp: 3;
  line-clamp: 3;
  overflow: hidden;
}
```

**The measurement.** Five declarations, not one, and each was tested on a
paragraph running to five lines clamped to three:

| | Result |
|---|---|
| all three prefixed properties, plus `overflow` | 3 lines, with an ellipsis |
| without `-webkit-box-orient: vertical` | 5 lines, no clamping, no warning |
| without `display: -webkit-box` | 5 lines, the same |
| the unprefixed `line-clamp` on its own | 5 lines; it is not Baseline yet |
| without `overflow: hidden` | the box is 3 lines, **but the rest of the text spills out below it** |

That last row is worth a note on the page. Measuring the element's height
reports three lines and looks correct; only looking at it shows the text
escaping the box.

The unprefixed `line-clamp` is emitted alongside the prefixed trio. It does
nothing today, as the fourth row shows, and costs one line to be right when
it ships.

### `fluid`

A **function**, not a mixin, and the page should say why: the hard part is the
value, and the value belongs to any property.

```scss
.heading { font-size: fluid(24px, 48px); }
.section { padding: fluid(16px, 64px) fluid(8px, 40px); }
.stack   { gap: fluid(0.5rem, 2rem); }
```

```css
.heading { font-size: clamp(1.5rem, 1rem + 2.5vw, 3rem); }
```

The preferred value is the line through `(min-viewport, min)` and
`(max-viewport, max)`:

```
slope     = (max - min) / (max-viewport - min-viewport)
intercept = min - slope * min-viewport
preferred = intercept + slope * 100vw
```

**The measurement.** Checked against hand arithmetic at a real 900px
viewport: the floor came out at 16.00px against 16.00 expected, the ceiling at
24.00 against 24.00, and an interpolated value at 19.52 against 19.52.

**The accessibility measurement, which is the reason the function exists.**
The preferred value keeps a `rem` term instead of being pure `vw`. Raising the
root font size, which is what browser text zoom does, moved the rem-bearing
value from 20.83px to 34.17px, while an equivalent `vw`-only value stayed at
19.74px and did not respond at all. A `vw`-only fluid value fails WCAG 1.4.4,
and that is exactly what a developer writing this by hand tends to produce.

### `loadify`, changed

It now respects `prefers-reduced-motion: reduce`. Previously it animated
regardless, which is an accessibility defect rather than a missing feature.

The page should explain why switching the animation off was not the fix. The
element starts at `opacity: 0` with `visibility: hidden`, and the animation is
what reveals it, so disabling the animation would have left the content
invisible for good. The end state is applied directly instead:

```css
@media (prefers-reduced-motion: reduce) {
  .a {
    opacity: 1;
    visibility: visible;
    backface-visibility: visible;
    animation: none;
  }
}
```

Verified with the media condition forced true: `opacity: 1`, visible,
`animation-name: none`, zero running animations. The normal path is unchanged,
proved by diffing the generated CSS against the previous version, where the
only difference is the added media block.

## Checking your work

Compiling is the only real check; a page can render a broken example
perfectly.

```bash
npm init -y && npm install gerillass@2.1.0

cat > check.scss <<'EOF'
@use "gerillass" as *;
.card    { @include container("card"); }
.title   { @include container-query("min", 400px) { font-size: 2rem; } }
.excerpt { @include line-clamp(3); }
.heading { font-size: fluid(24px, 48px); }
EOF

npx sass --load-path=node_modules/gerillass/scss check.scss
```

Then, for every example you publish:

1. **It compiles.** Paste it into the file above.
2. **It emits what the page claims.** An example that compiles can still be
   documented wrong.
3. **It emits something.** An unknown function name does not error in Sass, it
   is passed through as literal CSS, so an output containing the call itself
   means the name is wrong.

For `container-query`, add a fourth: **open it in a browser.** It is the one
member here whose output can be perfectly valid and still do nothing, if the
container ends up on the wrong element.
