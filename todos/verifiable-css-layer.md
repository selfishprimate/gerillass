# The Verifiable CSS Layer

Where a Sass mixin library stands while the industry moves to utility-first CSS
and AI coding agents write most of it. The numbers, what the community is
arguing about, and the gap nobody has closed.

Researched 12 September 2026, sources from January to September 2026, against
gerillass v2.1.0. The Turkish original was published as an artifact; this is
the English version kept with the repository.

---

## The thesis

| | |
|---|---|
| **92.7M** | weekly npm downloads of `tailwindcss`, September 2026 |
| **−80%** | Tailwind Labs revenue |
| **−40%** | Tailwind documentation traffic since 2023 |

On 7 January 2026 Tailwind Labs laid off three of its four engineers. Adam
Wathan said that without it the company would have gone under by the summer.
Over the same period Tailwind was downloaded more than ever.

That contradiction is the thesis of this report. AI did not reduce the *use*
of CSS libraries; it removed the *contact* between a library and the people
using it. Nobody goes to the docs to learn how to centre a div any more, they
ask an agent. Everything that ran on documentation traffic, the business model
and the reputation alike, went with that contact.

A library's value now depends less on how well it is explained than on how
correctly an agent can call it. That is where Gerillass has an opening, and
part of it is already written in this repository.

## The landscape, in numbers

Weekly npm downloads, pulled from the registry while this was written. The
Gerillass figure is the monthly total divided by weeks, because the weekly
endpoint is noisy at this volume.

| Package | Weekly downloads |
|---|---:|
| `tailwindcss` | 92,659,855 |
| `sass` | 22,318,469 |
| `@stylexjs/stylex` | 1,425,917 |
| `bourbon` | 130,163 |
| `open-props` | 21,336 |
| `gerillass` | ≈ 249 (1,078 a month) |

Bourbon, the library Gerillass is modelled on, is downloaded about 522 times
as often.

One conclusion follows, and it decides the rest of the strategy: **Gerillass
cannot compete on volume.** Any plan that aims to take share from Tailwind is a
fantasy. The useful question is whether there is a place where being small is
an advantage.

### The ground under preprocessors has gone

In the State of CSS 2026 survey Sass/SCSS is still the most picked
preprocessor, 2,032 of 3,656 respondents. The direction is down: Sass usage was
78% in 2024 and 62% in 2025. The survey's own commentary is blunter, saying
preprocessor usage "is declining and may soon be a thing of the past".

The cause is not a competitor, it is the browser. The three main reasons
people reached for Sass, variables, nesting and colour maths, are native CSS
now. Production use of native nesting grew 276% from 2024 to 2025.

What remains uniquely Sass is narrow and clear: **procedural logic.** Walking a
map with `@each`, `@for` loops, mixins that take parameters. In other words,
computation. Keep that in mind; it comes back at the end.

### Tailwind won, Tailwind Labs lost

In State of CSS 2026, 1,854 of the 3,697 people who answered the framework
question picked Tailwind. There is no argument about use. The same survey
also says that the biggest threat to Tailwind's crown may not be another
framework but no framework at all, pointing at design systems generated by
LLMs and at CSS's own evolution.

The irony is that LLMs defaulting to Tailwind sped up its spread and ended the
company's income. One developer summed it up: they never had to look at the
docs and never went to the website.

## What the community is arguing about

The real argument of 2026 is not which framework is better. The question has
become: **if an agent writes most of the code, which approach leaves it the
least room for error?**

### StyleX against Tailwind

Jared Palmer argues that StyleX's compile-time, typed style objects prevent
hallucination and ambiguity: no class-name strings for an agent to
misinterpret, no specificity collisions. Mark Dalgleish adds that Linear and
Cursor moved from Tailwind to StyleX.

Devon Govett objects, and his objection is the most useful one here: StyleX
has *no guardrails by default*. No colour tokens, no spacing scale, no font
size constraints. Consistency is left to discipline rather than enforced by
structure. Tailwind's opinionated defaults are a design system in themselves.

Both sides argue on the same axis: **constraint.** The less freedom an agent
has, the less it invents. That is an axis a mixin library is naturally good
at. There is nothing for an agent to invent in
`@include triangle(top, red, 10px)`; it either calls it correctly or the
library refuses with `@error`.

### Agent standards have settled

The Agent Skills format launched in October 2025, became an open standard in
December 2025, and by March 2026 32 tools read the same `SKILL.md` files,
among them Gemini CLI, Codex, Copilot, Cursor, JetBrains Junie, AWS Kiro and
Block Goose. Stripe, Figma, Notion, Cloudflare and Sentry publish their own.

It has a measured benefit. SkillsBench worked across 47,150 skills and found
curated skill libraries raised task pass rates by **16.2 percentage points**.
The same ecosystem has a quality problem: Snyk's February 2026 scan found at
least one security flaw in 36% of 3,984 skills. Curation and trust are a
differentiator on their own.

> **Caution: the weakly evidenced side.** Gerillass generates `llms.txt` and it
> is live on both domains. The evidence that the format works is contested. A
> study of 300,000 domains found 10.13% adoption and **no measurable increase in
> AI citations.** Google's John Mueller said server logs show AI bots not
> fetching the file.
>
> On the other side, Anthropic recommends it outright, OpenAI uses it for its
> SDK, and Chrome's Lighthouse 13.3 added a category in May 2026 that checks for
> it. So it is not dead, but it is not something to build a strategy on either.
> It costs nothing, so keep it; this is not where investment should go.

## The gaps

This is where the research was most productive. Agents write CSS and nobody
tells them whether what they wrote is right. That one sentence splits into four
gaps.

### 1. No verification at the level of the call

An agent writes a style, the result looks plausible, and it is wrong. The
industry's answer has been to give agents a feedback loop: with Chrome DevTools
MCP an agent can look at its output in a browser, and visual checks are
becoming an assertion an agent can make mid-flow. But all of these verify the
*rendered page*. Nothing verifies the *call* about to be written.

### 2. Accessibility is broken by default

An April 2026 review counts ten separate failures in a single sidebar
component: a missing landmark, a div instead of a heading, a clickable div
instead of a button, no `aria-expanded`, no keyboard handling, no focus
management. The fixes it proposes are on the React side (Radix, React Aria).
**There is no equivalent at the CSS layer.** Preventing it costs 3 to 8 minutes
a component; repairing it afterwards costs 45 to 90.

### 3. Computed CSS

An agent writes `flex items-center p-4` flawlessly. It does not reliably build
a triangle out of borders, work out the stops of a seven-colour gradient
stripe, or get the `clamp()` maths right for a fluid type scale. These are
exactly Sass's remaining territory, and exactly where agents are most often
plausible and wrong.

### 4. The library sits where an agent cannot see it

The Gerillass manifest, `gerillass.json`, exists only inside the npm package.
`gerillass.com/gerillass.json` answers 404. An agent that has not installed the
package cannot read the API; it guesses. This is exactly where shadcn's registry
and MCP setup wins: the LLM does not need to guess or hallucinate component
APIs, it queries what is actually there.

## What Gerillass already holds

The test discipline in this repository is the very thing the industry is only
now noticing it needs. As a technical fact rather than a marketing line:

- Every example in `meta/` is **compiled and snapshotted**. The manifest cannot
  claim an output the library does not produce.
- Every `rejects` entry must actually `@error`, and with **the library's own
  message** rather than a Sass internal error.
- Every example runs again under its `gls-` name and must produce
  **byte-identical CSS**.
- `gerillass.json` and `SKILL.md` are generated and committed; a stale commit
  fails the suite.

Nothing on the market matches this. shadcn's registry tells an agent *what
exists*; it does not *prove* an example produces the output it claims. Among the
Sass-related MCP servers, the only one that compiles a snippet and returns the
result is a general-purpose code runner with one star, and it does not compile
against any particular library.

> **The counterweight.** All of this sits inside a package downloaded 1,078
> times a month. The finding that a curated skill raises pass rates by 16.2
> points applies when the skill can be *found*. The Gerillass skill sits inside
> the npm tarball and is registered in no agent directory. There is something
> good here, currently in a place nobody can see.

## Repositioning

Positioning Gerillass as "a Sass library, an alternative to Tailwind" is a
fight already lost. The position the research points to is different:

> A callable, verifiable layer for the CSS that utility classes cannot express
> and agents cannot reliably compute.

This position has three things going for it. It is true: Sass's remaining
territory really is procedural logic, agents' weak spot really is computation,
and the two are the same set. It is not competitive: a mixin compiles to plain
CSS, so it can be used *alongside* Tailwind rather than instead of it. It is
defensible: the value of this layer comes from its verifiability, and the
verification machinery already exists here.

## Options

### A. Make the skill and the manifest visible · *do this first*

The generated `SKILL.md` exists but is locked inside the npm tarball. Agent
Skills is a standard read by 32 tools and needs no installation ceremony.
Serving `gerillass.json` over HTTP is a file copy; right now it is a 404.

This is the cheapest move with the highest return, because it opens a
distribution channel for work that is already done.

- **Cost:** a day or two. No new code, publishing and distribution work.
- **Risk:** low, reversible.
- **Evidence:** SkillsBench, curated skill libraries +16.2 points.

### B. `gerillass_compile`: a tool that verifies the call · *the real product*

An agent writes a mixin call, the tool compiles it against the library and
returns either the CSS it produces or **the library's own error message**. The
guessing loop closes at the level of the call rather than the page, which is
gap 1 exactly.

The `meta/`-driven test harness already does the hard half. It is also recorded
in this repository's own pending work as the one version of the MCP idea that
earns its place. The research confirms the space is empty.

- **Cost:** medium. The harness exists, the interface does not.
- **Risk:** distribution. Who installs an MCP server for a library they do not
  use? That is why it comes after A.
- **Evidence:** no competitor in the Sass MCP space; the only existing compiler
  is general-purpose with one star.

### C. Mixins that close what agents break · *one a release*

The failures the accessibility literature lists have no counterpart at the CSS
layer. The `focus-ring` and `prefers-reduced-motion` guard in this repository's
pending list are exactly these, and now have outside evidence behind them. An
agent can call a correct focus ring with a forced-colors fallback instead of
inventing `outline: none`.

- **Cost:** seven places per member; `/new-mixin` is that list.
- **Risk:** low, but it does not change the positioning on its own.
- **Evidence:** prevention 3 to 8 minutes, repair 45 to 90.

### D. Make verification independent of the library · *bigger, riskier*

Generalise the same harness into a tool that reports what any CSS or Sass
snippet actually produces and which Baseline features it uses. Its audience is
far wider than Gerillass's users.

But this is a new product, not a library feature, and it overlaps in part with
Chrome DevTools MCP. Only worth considering once A and B have taken hold.

### E. Publish the method · *reputation, not downloads*

The genuinely original asset is not the mixins, it is the discipline: a
generated manifest, compiled examples, rejections used as tests, a
byte-identity check. It can be written up as a pattern: how to make a library an
agent cannot misuse.

It will not bring downloads. But Tailwind Labs shows that in the agent era a
library's visibility no longer comes from documentation traffic; it comes from
the attention of agents and the people who build them.

---

## Recommendation

In order, because each step makes the next possible.

1. **Change the positioning.** The README, the site and the manifest
   description say "computed CSS that utilities cannot express" rather than "a
   Sass mixin library". It is a writing job, but it frames everything else.
2. **Put the skill and the manifest where agents can reach them.** Serve
   `gerillass.json` over HTTP, register the skill in agent directories. This
   opens the door in front of work already done.
3. **Write `gerillass_compile`.** First as a CLI, then as MCP. A CLI needs no
   installation: `npx gerillass check "..."` is something an agent can run
   immediately.
4. **Add `focus-ring` and the reduced-motion guard.** Already in the pending
   list, now with outside evidence. One a release, no rush.
5. **Measure, then expand.** Options D and E only make sense if steps 2 and 3
   made a measurable difference. If they did not, the library stays a
   well-maintained tool, which is also an outcome.

### What not to do

- **Turn it into utility classes.** A crowded field, arrived at late, and the
  opposite direction from Gerillass's advantage.
- **Build a strategy on `llms.txt`.** The evidence conflicts. Keep it, but do not
  put investment there.
- **Republish the manifest behind a protocol.** The note in `CLAUDE.md` is
  right: that file already ships in the package, and putting a server in front
  of it only adds an install step. MCP earns its place only by doing what a
  static file cannot, which is compiling.
- **Aim for documentation traffic.** That is Tailwind's lesson. Use can rise
  while traffic falls.

## Limits of this report

- The data visualisations on the State of CSS 2026 page itself were failing
  with query errors; the percentages come from quotations in search results,
  not from the primary table.
- The npm figures were pulled on a single day while this was written. Weekly
  variance can be large at these volumes.
- The effect of the Gerillass skill on agent success was not measured. The
  16.2 points from SkillsBench is a general finding, not a measurement of this
  library.
- The competitor survey was limited to Sass and CSS MCP servers. Closed-source
  and in-house tools are invisible to it.
